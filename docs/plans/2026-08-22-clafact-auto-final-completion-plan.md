# CLAFACT-AUTO 최종 완성 실행 계획

> **실행 담당자 필수 지침:** 이 문서는 작업 순서와 합격 기준을 고정한다. 구현할 때는 `executing-plans` 지침으로 작업을 하나씩 수행하고, `CLAFACT_AUTO_EXECUTION_CONTRACT.md`를 항상 최우선으로 적용한다.

**최종 목표:** 새로운 뉴스에서 수치 주장을 찾고, 여러 주장을 분리하고, 12개 정보를 구조화한 뒤, 국가통계포털의 공식 통계표·구조·값·발표정보를 직접 조회하고, 프로그램 계산으로 일치·불일치 또는 정확한 사람 확인 사유를 만드는 전체 과정을 완성한다.

**전체 방식:** 1,542건 전체를 개발 중에 반복 실행하지 않는다. 기존 실행 결과를 이용해 입력과 문제를 먼저 고정하고, 파이프라인을 앞 단계부터 차례대로 통과시키며 단계 결과를 모두 저장한다. 문제가 생기면 전체가 아니라 그 단계에서 멈춘 주장만 고친다. 모든 단계가 준비된 뒤 실제 공식 조회를 포함한 1,542건 최종 실행을 한 번 수행한다.

**사용 기술:** Python 3.12 이상, Pydantic v2, pytest, 국가통계포털 공식 API, 기존 `unified_claim_pipeline`과 공식 조회 엔진 v3

---

## 1. 이 계획이 필요한 이유

CLAFACT부터 CLAFACT-AUTO까지 한 달 이상 많은 기능을 만들었지만, 현재 결과만으로는 전체 서비스가 완성됐다고 말할 수 없다.

2026년 8월 22일 기준 1,542건 재실행 결과는 다음과 같다.

- 전체 원문 주장: 1,542건
- 공식 통계 검색 전에 멈춘 주장: 571건
- 공식 통계 검색에 들어간 주장: 971건
- 최종 자동 판정: 27건
- 확인된 국가통계포털 검색·구조 조회: 최소 24,825회
- 전체 자동 판정률: 약 1.8%

현재 상세 결과표는 1,542행·117열로 잘 저장돼 있다. 그러나 해당 실행은 `stored_slots_only: true`였다.

이는 다음을 의미한다.

- 기사 원문 전처리를 다시 실행하지 않았다.
- 기사에서 수치 주장을 새로 추출하지 않았다.
- 한 문장에 섞인 여러 주장을 다시 분리하지 않았다.
- 이전에 저장된 12개 정보에서 시작했다.

따라서 기존 결과는 중간 이후 단계의 상태를 확인하는 기준 자료로는 유용하지만, 기사 입력부터 최종 판정까지 전체 과정이 완성됐다는 증거는 아니다.

이번 계획은 단편적인 실패 건수 하나를 고치는 것이 아니라 다음 세 가지를 동시에 해결한다.

1. 모든 주장이 어느 단계에서 무엇을 입력받고 어떤 결과를 냈는지 기록한다.
2. 여러 주장 분리와 기사 문맥 보강 결과를 공식 통계 검증 과정에 실제로 다시 넣는다.
3. 마지막에는 기존 자료가 아닌 새로운 기사에서도 전체 과정이 작동하는지 평가한다.

## 2. 이번 주에 사용하지 않을 방식

### 2.1 1,542건 전체 반복 실행 금지

프로그램을 조금 고칠 때마다 1,542건을 다시 실행하지 않는다. 기존 실행에서 국가통계포털 검색·구조 조회만 최소 24,825회가 발생했다. 전체 반복은 시간과 공식 조회량을 낭비하고, 어느 수정이 효과가 있었는지 알기 어렵게 만든다.

### 2.2 특정 문장 전용 규칙 금지

주장 번호, 특정 기사 문장, 특정 통계표 번호를 조건으로 정답을 반환하는 코드는 만들지 않는다. 수정은 같은 유형의 새로운 주장에도 적용되는 공통 규칙이어야 한다.

### 2.3 저장된 공식값을 최종 판정에 재사용 금지

저장된 응답은 프로그램 계산과 결과 형식 시험에는 사용할 수 있다. 그러나 최종 운영 판정에서는 실제 국가통계포털과 공식 작성기관을 다시 조회해야 한다.

### 2.4 자동 판정률만 높이는 방식 금지

애매한 후보를 억지로 하나 고르면 자동 판정률은 올라가지만 잘못된 판정이 생긴다. 잘못된 자동 판정 0건이 자동 판정률보다 우선이다.

### 2.5 화면 꾸미기 우선 금지

남은 일주일은 핵심 처리 과정과 검증 기록 완성에 사용한다. 화면 디자인과 편의 기능은 핵심 과정이 통과한 뒤에만 다룬다.

## 3. 최종 처리 흐름

모든 새로운 기사는 반드시 아래 순서를 따른다.

```text
기사 입력
→ 기사 정리
→ 수치 주장 찾기
→ 여러 주장 분리
→ 12개 정보 구조화
→ 공식 통계 개념 연결
→ 국가통계포털 통계표 검색
→ 공식 통계표 구조 조회
→ 필수 조건 검사
→ 가장 알맞은 후보 확인
→ 정확한 공식값 위치 확정
→ 공식값 조회
→ 발표정보 조회
→ 프로그램 계산
→ 최종 판정
```

화면의 단일 검증, 여러 기사 일괄 검증, 명령어 실행, 1,542건 재실행은 모두 `core/unified_claim_pipeline.py`와 공식 조회 엔진 v3을 사용해야 한다.

## 4. 핵심 설계: 한 번 아래로 흘리고, 문제가 있는 부분만 다시 처리한다

### 4.1 원본 목록

최초 1,542건은 변경하지 않는 원본 목록으로 고정한다. 각 원문에는 고유 번호를 유지한다.

### 4.2 원문과 분리 주장 관계

한 문장에 여러 수치 주장이 있으면 각각 별도의 자식 주장으로 만든다.

예:

```text
원문 P-001
├─ 자식 P-001-01: 취업자는 10만 명 증가했다.
└─ 자식 P-001-02: 실업률은 3%로 하락했다.
```

원문 수 1,542건과 자식 주장 수를 섞지 않는다.

- 원문 처리율의 분모: 1,542건
- 실제 검증 결과의 분모: 분리 후 만들어진 전체 자식 주장 수

### 4.3 단계별 결과 기록

각 주장은 모든 단계에서 다음 정보를 남긴다.

- 원문 번호
- 자식 주장 번호
- 단계 이름
- 단계 입력
- 단계 결과
- 통과·사람 확인·검증 제외·외부 조회 실패 상태
- 멈춘 이유
- 공식 조회 종류와 횟수
- 공식 응답 주소·조회 시각·내용 확인값
- 프로그램 버전과 자료 버전
- 다음에 시작할 단계

### 4.4 단계 통과문

앞 단계가 합격한 주장만 다음 단계로 보낸다.

- 12개 정보가 부족하면 통계표 검색으로 보내지 않는다.
- 공식 통계 개념이 확정되지 않으면 통계표를 억지로 선택하지 않는다.
- 공식 구조가 없으면 정확한 공식값 위치를 추정하지 않는다.
- 공식값과 발표정보가 없으면 자동 판정하지 않는다.

### 4.5 부분 재실행

수정 후 다시 처리하는 범위는 다음과 같다.

- 문장 분리 수정: 해당 문장과 새 자식 주장만 다시 처리
- 12개 정보 수정: 해당 주장부터 다시 처리
- 통계 개념 사전 수정: 영향을 받는 개념의 주장만 다시 처리
- 위치 찾기 수정: 해당 통계표 후보의 주장만 다시 처리
- 계산 수정: 동일 계산 종류의 주장만 다시 처리

완료된 다른 주장과 구간은 다시 처리하지 않는다.

## 5. 최종 산출물 구조

최종 실행 결과는 아래 폴더에 한 실행 단위로 저장한다.

```text
artifacts/clafact_final_completion_202608/
├─ 00_run_manifest.json
├─ 01_source_registry.jsonl
├─ 02_claim_lineage.jsonl
├─ 03_stage_events.jsonl
├─ 04_claim_final_results.jsonl
├─ 05_official_request_log.jsonl

├─ 07_claim_detail.csv
├─ 08_evaluation_report.json
├─ 09_evaluation_report.txt

```

### 각 파일의 역할

- `00_run_manifest.json`: 실행 시각, 코드 변경번호, 자료 버전, 설정, 전체 파일 확인값
- `01_source_registry.jsonl`: 최초 1,542건 원문과 기사 정보
- `02_claim_lineage.jsonl`: 원문과 분리된 자식 주장 관계
- `03_stage_events.jsonl`: 주장별 모든 단계의 입력·출력·상태
- `04_claim_final_results.jsonl`: 각 자식 주장의 최종 결과
- `05_official_request_log.jsonl`: 국가통계포털과 공식 작성기관 요청 기록
- `06_stage_summary.csv`: 단계별 입력·통과·중단·실패 수
- `07_claim_detail.csv`: 사람이 엑셀에서 확인할 수 있는 주장별 전체 상세
- `08_evaluation_report.json`: 프로그램이 검사할 수 있는 평가 결과
- `09_evaluation_report.txt`: 사용자가 읽을 수 있는 쉬운 최종 보고
- `checkpoints/`: 단계가 끝날 때마다 이어서 실행할 수 있는 중간 저장 파일

## 6. 단계별 작업과 합격 기준

## 단계 0. 입력과 기준 결과 고정

### 할 일

1. 기존 1,542건의 입력 번호와 원문을 고정한다.
2. 기존 117열 결과표와 실행 결과를 원문 번호로 연결한다.
3. 처음 멈춘 단계와 최종 중단 이유를 대조한다.
4. 둘이 다르면 더 앞에서 멈춘 단계를 주된 문제 단계로 기록한다.
5. 기존 자동 판정 27건을 성공 보호 자료로 고정한다.

### 저장 내용

- 원문 번호
- 기사 번호
- 문장 번호
- 기사 작성일
- 원문
- 기존 12개 정보
- 기존 첫 중단 단계
- 기존 최종 결과
- 재처리 시작 단계

### 합격 기준

- 원문 1,542건이 모두 존재한다.
- 원문 번호 중복 0건
- 원문 누락 0건
- 기존 결과와 연결되지 않은 원문 0건
- 27개 기존 자동 판정이 모두 보호 목록에 포함된다.

### 효과

이후 숫자가 달라져도 원문이 사라졌는지, 자식 주장이 늘어난 것인지 구분할 수 있다.

## 단계 1. 기사 정리와 문맥 확보

### 할 일

1. 기사 제목, 대상 문장, 앞뒤 문장, 기사 작성일을 하나의 입력으로 묶는다.
2. 기사 본문이 저장돼 있으면 해당 본문을 사용한다.
3. 본문이 없으면 `본문 없음`으로 기록하고 임의로 문맥을 만들지 않는다.
4. 문맥은 빠진 정보를 보완하는 데만 사용하고 원문 주장의 의미를 바꾸지 않는다.

### 합격 기준

- 모든 원문에 기사 입력 상태가 기록된다.
- 기사 작성일을 알 수 없는 경우가 별도 상태로 구분된다.
- 본문이 없는데 문맥이 있다고 기록한 건수 0건
- 문맥에서 보완한 정보는 출처 문장 위치가 남는다.

## 단계 2. 수치 주장 찾기와 재분류

### 분류

- 공식 통계로 검증할 수 있는 수치 주장
- 여러 주장으로 분리해야 하는 문장
- 기사 문맥이 더 필요한 주장
- 전망·가정·목표·의견
- 정확한 값이 없는 정성 표현
- 수치 검증 대상이 아닌 문장

### 합격 기준

- 모든 원문에 하나 이상의 처리 결과가 있다.
- 분류 결과가 없는 원문 0건
- 검증 제외 문장에는 제외 이유가 있다.
- 기사 문맥이 필요한 문장에는 부족한 정보 종류가 기록된다.

## 단계 3. 여러 주장 분리

### 할 일

1. 서로 다른 지표·값·기간·지역·비교·계산은 별도 자식 주장으로 분리한다.
2. 각 자식 주장에 고유 번호를 부여한다.
3. 자식 주장에 원문 전체와 목표 수치 표현을 함께 보존한다.
4. 모든 자식 주장을 다시 12개 정보 구조화 단계로 보낸다.

### 합격 기준

- 원문과 자식 관계 누락 0건
- 같은 자식 번호 중복 0건
- 분리 과정에서 원문 수치가 사라진 건수 0건
- 서로 다른 두 판정을 하나의 자식 주장에 남긴 건수 0건
- 분리된 모든 자식 주장이 다음 단계 또는 정확한 중단 상태를 가진다.

## 단계 4. 12개 정보 구조화와 전수검사

### 기록할 12개 정보

1. 지표
2. 주장값
3. 단위
4. 대상 시점
5. 월·분기·연간 구분
6. 지역
7. 대상 집단
8. 성별·연령·산업·품목 등 세부 조건
9. 비교 방식
10. 계산 방식
11. 추가 조건
12. 기사 출처 힌트

### 각 정보의 상태

- 원문에서 확인
- 기사 문맥에서 확인
- 프로그램이 표준 표현으로 변환
- 정보 부족
- 정보 충돌
- 해당 없음

### 합격 기준

- 모든 자식 주장에 12개 항목 자체가 존재한다.
- 자동 검증에 필요한 필수 정보가 비어 있는데 다음 단계로 간 건수 0건
- 주장값·단위·시점을 원문 근거 없이 추정한 건수 0건
- 비교 주장에는 기준 시점 또는 기준 대상이 기록된다.
- 계산 종류와 필요한 공식값 개수가 기록된다.

## 단계 5. 공식 통계 개념 연결
