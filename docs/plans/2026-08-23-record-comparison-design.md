# 역대 최대·최소 공식 검증 설계

## 목적

뉴스의 `역대 최대`, `역대 최저` 표현을 단순 현재값 주장과 기록 비교 주장으로 구분하고, 선택된 KOSIS 공식 좌표의 비교 가능한 전체 과거 기간을 실제 조회하여 Python으로 기록 여부를 판정한다.

## 선택한 방식

기존 공통 공식 검증 엔진에 기록 비교 계산을 정식 추가한다. 별도 후처리 서비스나 저장된 최대값 표는 만들지 않는다. 따라서 Streamlit·배치·CLI가 동일한 Catalog 검색, 공식 메타데이터, Hard Guard, 좌표 확정, 공식값·공표정보 조회와 실행 추적을 사용한다.

## Claim 구조

- 문장에 현재 수치와 기록 표현이 함께 있으면 현재 수치 Claim과 기록 비교 Claim을 구분한다.
- 기록 비교 Claim은 `comparison.type`을 `RECORD_HIGH` 또는 `RECORD_LOW`로 유지한다.
- 현재 수치가 원문에 있으면 그 값을 기록 비교 Claim의 비교 대상값으로 사용한다.
- 현재 수치·단위·대상 기간 중 하나라도 확정되지 않으면 공식 조회에 억지로 진입시키지 않고 부족한 항목을 기록한다.
- 동일한 기록 표현이 포함된 신규 Claim에 적용하며 특정 Claim ID나 문장을 조건으로 사용하지 않는다.

## 공식 조회 범위

- Catalog와 공식 메타데이터로 현재 기간의 Evidence 좌표를 먼저 확정한다.
- 선택된 통계표의 공식 시작 기간부터 Claim 대상 기간까지 같은 항목·지역·대상·차원·주기의 좌표를 만든다.
- Claim 기간 이후 값과 기사 시점에 아직 공표되지 않은 값은 제외한다.
- `fetch_many`를 이용해 같은 좌표의 기간 범위를 공식 API로 조회하고 각 값의 출처, 조회시각, 응답 해시, 공표 근거를 보존한다.
- 공식 시작 기간을 알 수 없거나 비교 기간을 안전하게 열거할 수 없으면 단계별 reason code로 HOLD한다.

## 결정론적 계산과 판정

- `RECORD_HIGH`: 비교 범위의 `max(values)`를 계산한다.
- `RECORD_LOW`: 비교 범위의 `min(values)`를 계산한다.
- 현재 공식값이 계산된 최대·최소값과 같으면 기록 주장을 지지한다. 동률 기록도 인정한다.
- 현재 수치 Claim은 기존 `DIRECT_VALUE` 판정을 그대로 사용한다.
- LLM은 공식값, 최대·최소값, 최종 판정을 생성하지 않는다.

## 감사 기록

결과에는 다음을 남긴다.

- 기록 비교 종류와 범위
- 조회한 최초·최종 기간과 비교값 개수
- 기록값과 기록 달성 기간
- 모든 Evidence 좌표와 공식값 출처
- 공식 응답 해시와 공표 근거
- 각 파이프라인 단계 실행 상태

## 오류 처리

- 공식 Catalog·메타데이터·값·공표정보 요청 실패는 기존 실행 계약의 단계별 reason code를 사용한다.
- 공식 조회를 하지 않은 전처리 실패와 공식 조회 후 HOLD를 구분한다.
- 값이 일부만 수집되면 전체 기간 기록을 확정하지 않고 HOLD한다.
- 서로 다른 단위·주기·차원의 값은 하나의 기록 비교에 섞지 않는다.

## 검증 범위

1. 계산기의 최대·최소 및 동률 단위 테스트
2. 공식 시작 기간부터 Claim 기간까지의 기간 좌표 생성 테스트
3. 기록 비교 Claim의 계약·계산 계획 테스트
4. 공식값 일부 누락·공표정보 실패 HOLD 테스트
5. 공통 엔진에서 공식값 전체를 사용한 Verdict·실행 추적 통합 테스트
6. 해당 패턴의 작은 Registry 묶음 실행과 개선 전후 CSV 기록

전체 1,542건 재실행은 이 묶음의 완료 조건이 아니다. 작은 묶음의 코드·공식 조회·CSV 증거가 통과한 뒤 다음 문제 묶음으로 이동한다.
