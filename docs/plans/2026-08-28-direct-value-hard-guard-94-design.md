# 직접값 좌표 병목 94건 공통 규칙 설계

## 목표

직접값 미해결 176건의 단계별 평가표에서 `필수 조건 검사` 단계에 멈춘 94건을 대표 원인별로 전량 분류한다. 그중 실제 좌표 변환 문제로 확인된 묶음에만 일반 규칙을 적용하고, 동일 94건을 KOSIS 공식 API로 다시 실행하여 개선 전후 결과를 한 행 단위로 기록한다.

## 확인된 현재 상태

- 전체 대상: 94건
- `NO_HARD_GUARD_CANDIDATE`: 56건
- `NO_EVIDENCE_COORDINATE_CANDIDATE`: 38건
- 후보 거절 사유가 관측된 Claim 수(중복): 단위 69건, 기간 범위 51건, 주기 48건, 대상·품목 차원 39건, 구조정보 36건, 지역 11건
- 위 숫자는 배타적 대표 원인 수가 아니다. 한 Claim에서 여러 후보가 서로 다른 이유로 탈락한 결과다.
- 일부 Claim은 좌표 문제가 아니라 잘못된 지표·값 역할·검증 유형 때문에 이 단계에 도달했다. 예를 들어 부동산 매입액을 `총인구`로 구조화한 Claim은 좌표 규칙을 완화해서는 안 된다.

## 선택한 접근

### 1. 대표 원인 분류를 먼저 수행한다

각 Claim에 후보 전체의 Hard Guard 진단, Evidence 해석 결과, 원문과 검색 명세를 결합하여 대표 원인 하나와 보조 원인 목록을 기록한다.

대표 원인 우선순위는 다음과 같다.

1. `CLAIM_STRUCTURE_ERROR`: 원문의 검증 대상과 구조화된 지표·값 역할이 다름
2. `NON_KOSIS_OFFICIAL_ROUTE`: 협회·기업·해외기관 등 KOSIS 밖의 공식자료가 필요함
3. `UNIT_COORDINATE_GAP`: 같은 통계 개념이지만 공식 단위·배율 표현을 연결하지 못함
4. `PERIOD_FREQUENCY_GAP`: 같은 통계 개념이지만 기사 기간을 공식 주기·기간 코드로 변환하지 못함
5. `REGION_COORDINATE_GAP`: 전국 표현 또는 행정지역 표현을 공식 지역 차원에 연결하지 못함
6. `DIMENSION_COORDINATE_GAP`: 품목·산업·연령·대상 표현을 공식 분류 멤버에 연결하지 못함
7. `METADATA_GAP`: 공식 후보는 있으나 구조정보가 불완전함
8. `SEMANTIC_COORDINATE_AMBIGUITY`: 여러 좌표가 남아 의미적으로 하나를 확정할 수 없음

대표 원인은 결정 근거와 함께 CSV에 저장한다. 분류기는 Claim ID나 문장 전체를 하드코딩하지 않고 슬롯, 원문 역할, 후보 메타데이터, 안정적인 진단 코드만 사용한다.

### 2. 좌표 규칙은 안전한 경우에만 적용한다

- 단위: 같은 물리량 안에서만 배율을 정규화한다. `원↔억원↔조원`, `달러↔천달러↔억달러`, `명↔천명↔만명`을 지원한다. 원화와 달러처럼 통화가 다른 값은 자동 환산하지 않는다.
- 기간·주기: 연·분기·월·누계를 공식 `PRD_SE/PRD_DE` 형식으로 변환한다. 기간이 상대 표현이고 기사 작성일로 확정되지 않으면 통과시키지 않는다.
- 지역: `한국·대한민국·전국`은 전국 좌표로 통일한다. `국내`는 문맥상 국가 범위를 뜻할 때만 전국으로 본다. `전체`나 잘못 추출된 표현은 자동 변환하지 않는다.
- 차원: 공식 메타데이터에 존재하는 정확한 멤버 또는 검증된 동의어만 연결한다. 후보에 없는 품목·산업·대상은 강제로 Top-1에 연결하지 않는다.
- 지표·측정 종류: Claim의 값 역할과 공식 항목의 측정 종류가 일치해야 한다. 금액을 인구, 개수를 지수, 환산 금액을 원 통계값으로 연결하지 않는다.

### 3. 기존 파이프라인을 그대로 사용한다

공통 규칙은 별도 판정 엔진을 만들지 않고 기존 순서에 연결한다.

```text
검색 명세
→ KOSIS Catalog API
→ 공식 구조정보 API
→ Hard Guard
→ Evidence Cell Resolution
→ KOSIS 공식값 API
→ 공표정보 확인
→ Python 판정
```

규칙 적용 전후의 동일 Claim이 같은 Core Engine을 통과해야 하며 Streamlit·배치·CLI의 판정 계약을 바꾸지 않는다.

## 재실행과 평가

94건만 별도 Registry로 만들고 실제 공식 API를 호출한다. 결과표에는 다음을 기록한다.

- Claim 번호와 원문 해시
- 개선 전 실패 단계·사유
- 대표 원인과 보조 원인
- 적용된 공통 규칙
- 개선 후 단계별 상태
- 확정된 공식 좌표
- 공식값·출처 URL·응답 해시·공표 상태
- 엄격한 공식 판정 완료 여부
- 신규 Claim 적용 범위

## 완료 조건

1. 94건 모두 대표 원인과 근거가 기록된다.
2. Claim별 하드코딩 없이 공통 규칙이 구현된다.
3. 안전하지 않은 Claim 구조 오류는 좌표 탐색에서 차단된다.
4. 좌표 규칙 대상은 실제 KOSIS 공식 API로 재실행된다.
5. 개선 전후의 단계 이동과 엄격 공식 판정 증감이 계산된다.
6. 공식 좌표·값·URL·응답 해시·공표정보가 보존된다.
7. 관련 회귀 테스트와 전체 테스트를 통과한다.
