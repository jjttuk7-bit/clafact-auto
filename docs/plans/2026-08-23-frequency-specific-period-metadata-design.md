# 주기별 공식 통계 기간 메타데이터 설계

## 목적

KOSIS 통계표가 연·분기·월 자료를 함께 제공할 때 각 주기의 공식 시작·종료 기간을 따로 보존한다. `역대 최대·최소` Claim은 Claim과 같은 주기의 공식 기간만 사용하여 과거 전체 비교 범위를 만들고, 기간을 추정하지 않는다.

## 현재 문제

- 공식 메타데이터 응답에는 연·분기·월의 시작·종료 기간이 각각 존재한다.
- 현재 코드는 여러 주기를 하나의 `frequency`, `start_period`, `end_period`로 합친다.
- 이 과정에서 월별 시작 기간이 사라지고, 분기 시작값이 전체 시작값처럼 선택될 수 있다.
- 예를 들어 `1999년 3분기`를 `1999년 6월`로 바꾸는 것은 공식 근거가 없는 추정이다.
- 따라서 안전장치가 이를 보류시키며, 월별 `역대 최대` 비교가 과거 전체 값 조회까지 진행하지 못한다.

## 선택한 방식

KOSIS 후보에 주기별 기간 범위를 구조화하여 저장한다.

- 주기는 `년`, `분기`, `월`로 정규화한다.
- 각 주기마다 공식 `시작 기간`과 `종료 기간`을 별도로 보존한다.
- 같은 주기의 행이 여러 개면 그 주기 안에서만 가장 이른 시작과 가장 늦은 종료를 선택한다.
- 기록 비교 계획은 Claim 주기와 정확히 같은 범위만 선택한다.
- 정확한 범위가 없거나 형식이 모호하면 계산 계획을 만들지 않고 보류 사유를 남긴다.
- 기존 단일 주기 후보와 저장 데이터는 계속 읽을 수 있도록 기존 필드를 유지한다.

## 데이터 구조

KOSIS 후보에 다음 의미의 필드를 추가한다.

```text
period_ranges:
  월: {start_period: "1999.06", end_period: "2026.07"}
  분기: {start_period: "1999 3/4", end_period: "2026 2/4"}
  년: {start_period: "2000", end_period: "2025"}
```

`frequency`, `start_period`, `end_period` 기존 필드는 호환성을 위해 유지한다. 다만 여러 주기가 섞인 후보의 기록 비교에서는 기존 통합 필드를 사용하지 않는다.

## 파이프라인 동작

1. 기존 KOSIS 공식 메타데이터 요청에서 기간 행을 받는다.
2. 기간 행을 주기별로 묶고 공식 시작·종료 기간을 보존한다.
3. Catalog 후보 직렬화와 다시 읽기 과정에서도 이 구조를 유지한다.
4. 현재 값의 Evidence 주기와 Claim 주기를 확인한다.
5. 같은 주기의 공식 시작 기간부터 Claim 대상 기간까지 비교 기간을 만든다.
6. 기존 공식값·공표정보 조회와 결정론적 최대·최소 계산을 수행한다.

## 안전 원칙

- 분기 시작값으로 월 시작값을 만들지 않는다.
- 연 시작값으로 분기·월 시작값을 만들지 않는다.
- 서로 다른 주기의 값은 같은 기록 비교에 섞지 않는다.
- 주기 또는 시작 기간이 불명확하면 공식값을 임의 생성하거나 기간을 추정하지 않는다.
- 특정 Claim ID나 특정 문장을 조건으로 사용하지 않는다.

## 검증 기준

- 연·분기·월이 함께 있는 공식 메타데이터가 주기별 범위로 정확히 보존된다.
- 월별 Claim은 월별 시작 기간만 사용한다.
- 단일 주기 기존 후보는 이전과 동일하게 동작한다.
- 주기별 범위가 없는 혼합 후보는 안전하게 보류된다.
- 저장·재로딩 후에도 주기별 범위가 유지된다.
- 선택된 실제 Claim `A02558_7`을 다시 실행하여, 월별 공식 시작 시점에서 과거 전체 비교 계획이 생성되는지 CSV와 실행 기록으로 확인한다.
- 실제 과거값 또는 공표정보가 일부라도 부족하면 `역대 최대`를 확정하지 않고 정확한 단계와 사유로 보류한다.

전체 1,542건 재실행은 이번 묶음의 완료 조건이 아니다. 이 패턴의 대표 Claim 한 건으로 공식 메타데이터 보존, 전체 기간 조회 진입, 결과 기록까지 검증한 뒤 다음 문제 묶음으로 이동한다.
