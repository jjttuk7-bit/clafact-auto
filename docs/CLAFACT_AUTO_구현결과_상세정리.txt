0. 문서의 목적
---------------

이 문서는 CLAFACT-AUTO에서 지금까지 실제로 구현된 결과를 개발 순서에 따라 정리한 현황 문서다.
설계만 존재하는 항목과 코드·테스트로 구현된 항목을 혼동하지 않도록 현재 저장소의 코드, 데이터,
Git 이력, pytest 실행 결과를 기준으로 작성했다.

CLAFACT-AUTO의 목적은 뉴스 기사 속 수치 Claim을 KOSIS 공식 통계와 자동 대조하는 것이다.
이 시스템은 답을 그럴듯하게 생성하는 서비스가 아니라 다음 조건을 만족할 때만 자동 판정하는
근거 중심 검증 엔진이다.

  1) KOSIS 공식값은 LLM이 만들지 않는다.
  2) 공식값은 KOSIS API 또는 저장된 공식 Snapshot에서만 읽는다.
  3) 수치 계산은 Python 함수가 수행한다.
  4) LLM은 Claim 해석을 위한 Structured Output에만 사용한다.
  5) Hard Guard가 Semantic Score보다 먼저 실행된다.
  6) 후보가 모호하면 Top-1을 강제로 선택하지 않고 HOLD/HUMAN_REVIEW로 보낸다.
  7) 모든 핵심 결과에는 근거 좌표, 계산 결과, 사유 코드, 버전 정보를 남긴다.

2. 데이터 계약 구현: 자유 텍스트에서 구조화 객체로 전환
-------------------------------------------------------

뉴스 문장 자체를 내부 검증 계약으로 사용하지 않도록 Pydantic 스키마를 구현했다.
모든 스키마는 extra="forbid"를 사용하여 정의되지 않은 필드가 임의로 유입되는 것을 막는다.

2.1 ClaimSchema와 12개 Semantic Slot

실제 12개 의미 슬롯은 다음과 같다.

  1) indicator   : 검증할 지표 또는 항목
  2) value       : 기사에 제시된 수치
  3) unit        : %, 명, 천명, 원, 지수 등의 단위
  4) time        : 기준 시점 또는 기간
  5) frequency   : 월, 분기, 연 등 통계 주기
  6) region      : 전국, 시도 등 공간 범위
  7) population  : 연령·산업·대상 집단 등 모집단
  8) dimension   : 성별·연령·품목 등 KOSIS 분류 조건
  9) comparison  : 전년 동월 대비, 전월 대비 등 비교 기준
 10) calculation : DIRECT_VALUE, GROWTH_RATE 등 계산 유형
 11) condition   : 계절조정, 원계열, 잠정/확정 등 통계 조건
 12) source_hint : 기사 안의 KOSIS·통계청 등 출처 단서

추적과 라우팅을 위한 별도 메타 필드:

  claim_id, source_sentence, parse_status, parse_reason

parse_status는 AUTO_OK, HOLD, HUMAN_REVIEW 중 하나만 허용한다.

2.2 나머지 핵심 계약

  - StandardConceptSchema: 의미 표준 매핑 결과
  - KosisCandidateSchema: 후보 통계표와 항목·차원·단위·주기 메타데이터
  - HardGuardResult: 구조적 통과 여부와 reject code
  - MatchResult: 의미 점수, Top1/Top2 margin, 경로 상태
  - EvidenceCellSchema: org/tbl/itm/obj/member/기간/차원 코드로 구성된 증거 셀
  - CalculationPlan: 계산 유형, 필요 Evidence Cell, 연산자, 허용 오차
  - VerdictSchema: 기사값, 공식값, 계산값, 판정, 경로, 근거, 버전, 실행 추적
  - PipelineTraceSchema: 단계별 PASS/HOLD/HUMAN_REVIEW/SKIPPED 기록

관련 파일:

  schemas/claim.py
  schemas/concept.py
  schemas/candidate.py

3. Claim Extraction, Split, Structured Parsing 구현
--------------------------------------------------

3.1 복합 Claim 분리

core/claim_splitter.py의 split_complex_claim()은 한 문장 안의 복수 수치 주장을 독립 Claim으로
분리한다. 분리할 수 없는 복합 의미를 임의로 하나만 선택하지 않는다.

3.2 Structured Output Parser

core/claim_parser.py는 StructuredClaimExtractor Protocol을 통해 모델 구현과 핵심 로직을 분리한다.
core/hcx_claim_extractor.py는 HCX 호출 결과를 JSON Schema에 맞춘 12 Slot 구조로 받는다.
자유 형식 설명문은 판정 계약으로 사용하지 않는다.

파싱 후 필수 조건이 충분하면 AUTO_OK, 모호하거나 필수 문맥이 빠지면 HOLD 또는
HUMAN_REVIEW로 라우팅한다. 상대 시점은 core/claim_time_resolver.py에서 기사 기준일을 사용해
결정론적으로 보정한다.

3.3 parser 안정화

HCX가 유효한 frequency를 반환한 경우 Claim이 누락되던 문제를 수정했고, 전년 동월 대비 등
비교 문장의 방향(상승/하락 부호)이 보존되도록 보완했다.

관련 파일:

7. Hard Guard 우선 실행 구현
----------------------------

Hard Guard는 의미 점수 계산보다 먼저 실행된다. 구조적으로 맞지 않는 후보는 점수가 높아도
Semantic Matching 대상에 들어가지 않는다.

현재 검사 항목과 대표 reject code:

  - 미완성 live metadata       -> METADATA_INCOMPLETE
  - 통계 주기 충돌              -> FREQUENCY_CONFLICT
  - 단위 충돌                   -> UNIT_CONFLICT
  - 연령 차원 누락              -> AGE_DIMENSION_REQUIRED
  - 성별 차원 누락              -> SEX_DIMENSION_REQUIRED
  - 지역 세분 수준 충돌         -> REGION_GRANULARITY_CONFLICT
  - 통계 제공 기간 밖의 시점    -> TIME_NOT_AVAILABLE
  - 전망·예측·예상 Claim        -> FORECAST_CLAIM

Hard Guard를 통과한 후보가 하나도 없으면 자동 Verdict를 만들지 않고 HOLD한다.

관련 파일:

  core/hard_guard.py
  tests/unit/test_catalog_search_and_hard_guard.py


8. Semantic Matching과 모호성 제어 구현
---------------------------------------

Hard Guard 생존 후보만 semantic_match()가 점수화한다.

현재 기본 기준:

  minimum_score = 0.7
  min_margin    = 0.1

점수는 지표명/표명/항목명의 문자열 유사도에 단위와 주기 호환성을 더해 계산한다.
결정 규칙은 다음과 같다.

  - score < minimum_score       -> HOLD / LOW_SEMANTIC_SCORE
  - Top1-Top2 margin < 0.1      -> HOLD / AMBIGUOUS_MARGIN
  - 두 조건을 모두 통과         -> AUTO / MATCH_ACCEPTED
  - Top1이 아닌 나머지 후보     -> HOLD / NON_TOP_CANDIDATE

따라서 모호한 후보를 강제로 Top-1으로 선택하지 않는다.

관련 파일:

  core/semantic_matcher.py
  core/unit_normalizer.py
  tests/unit/test_semantic_matcher.py

10. KOSIS 공식값 조회와 기사시점 안전성
----------------------------------------

10.1 API 조회

Evidence Cell이 확정된 뒤에만 KOSIS API 요청 파라미터를 만든다. KOSIS OpenAPI transport,
HTTP client, parameter data adapter를 핵심 로직과 분리했다. 환경변수에 API 키가 있어도 좌표가
불완전하면 아무 표의 값을 임의로 가져오지 않는다.

10.2 공식 Snapshot

API가 기사시점의 공표값을 재현하지 못하거나 네트워크가 불가능한 경우 저장된 공식 Snapshot을
사용한다. 현재 data/kosis_snapshots 아래 공식 근거 파일은 16개다.

Snapshot 정책:

  - 공식 KOSIS 응답 또는 확인된 공식값만 저장
  - 요청 파라미터와 응답 hash를 보존
  - 기사 날짜 이후 발표된 값은 자동 근거로 사용하지 않음
  - 기존 Snapshot을 덮어쓰기보다 새 버전을 추가
  - API 조회 실패 시에도 검증 가능한 dated snapshot이 있으면 안전하게 fallback

기사시점 공식값이 없으면 VALUE_UNAVAILABLE 또는 기사시점 관련 HOLD 사유로 종료한다.

11. 결정론적 Calculation Engine 구현
------------------------------------

core/calculator.py에서 다음 계산을 Python 함수로 수행한다.

  DIRECT_VALUE : 공식 셀 한 개의 값을 그대로 사용
  GROWTH_RATE  : (현재값 - 기준값) / 기준값 * 100
  DIFFERENCE   : 현재값 - 기준값
  RATIO        : 분자 / 분모
  MULTIPLE     : 분자 / 분모
  SHARE        : 여러 분자 합 / 마지막 분모 * 100
  RANK         : 첫 값보다 큰 비교값 개수를 이용한 순위
  THRESHOLD    : 기준 이상이면 1.0, 미만이면 0.0

입력 셀 개수 검증과 0으로 나누기 차단이 포함되어 있다. 계산 과정에서 LLM은 사용되지 않는다.

관련 파일:

12. Verdict Engine과 안전 라우팅 구현
------------------------------------

최종 판정 유형:

  MATCH         기사값과 계산된 공식값이 허용오차 안에서 일치
  MISMATCH      공식 근거는 확정됐지만 기사값이 허용오차 밖
  UNDETERMINED  공식 근거·좌표·시점·계산 조건이 충분하지 않음

운영 경로:

  AUTO          자동 검증 조건 충족
  HOLD          근거 부족, 후보 모호, 공식값 부재 등으로 자동 확정 중지
  HUMAN_REVIEW  문맥 해석 등 사람의 검토가 필요

13. 등록형 CPI 상세품목 증감률 검증 구현

15. 크롤링 뉴스 배치 검증 구현
--------------------------------

한 문장이 아니라 크롤링된 기사 파일 전체를 업로드하는 흐름을 구현했다.

지원 입력:

  - CSV: UTF-8 BOM, UTF-8, CP949 처리
  - JSON: 객체 배열
  - XLSX: 첫 시트의 헤더와 행

지원 컬럼명:

  표준 컬럼    article_id, published_at, body, title, source_url
  주요 별칭    id, date, content, sentence, text, 본문, 문장, 기사본문, 내용,
               뉴스본문, 제목, 기사제목, url, link 등

published_at이 없는 파일은 UI에서 제공한 기본 기사 기준일을 사용할 수 있다. body가 없고 title만
있는 문장형 파일은 title을 검증 본문으로 사용할 수 있다.

처리 원칙:

  - 기사별 전처리 후 숫자가 있는 Claim 후보를 모두 독립 검증
  - 한 Claim의 오류가 전체 배치를 중단하지 않음
  - 예외 Claim은 BATCH_VERIFIER_ERROR로 HOLD
  - 기사별 MATCH/MISMATCH/검토 필요 수 집계

다운로드 XLSX 시트:

  Claim Results    Claim별 기사값, 계산값, Evidence, 표 ID, 사유
  Article Summary  기사별 Claim 수와 ALL_MATCH/NEEDS_REVIEW/MISMATCH_FOUND
  Review Queue     AUTO가 아닌 Claim만 모은 검토 큐

관련 파일:

  core/batch_verifier.py
  app/streamlit_app.py
  tests/unit/test_batch_verifier.py


16. 기존 CLAFACT 검토 콘솔 연동 경계

18. 감사 가능한 3갈래 Pipeline Trace 구현
------------------------------------------

사용자가 최종 판정뿐 아니라 전체 과정의 성공·중단 지점을 확인할 수 있도록 단계 추적을 구현했다.

전체 stage 계약:

  PREPROCESS
  SENTENCE_SPLIT
  CLAIM_CANDIDATE_SELECTION
  CLAIM_SPLIT
  CLAIM_PARSE
  SEMANTIC_MAPPING
  CATALOG_SEARCH
  HARD_GUARD
  SEMANTIC_MATCH
  EVIDENCE_CELL
  OFFICIAL_VALUE_FETCH
  CALCULATION
  VERDICT

각 이벤트에는 stage, status, reason_code, output_ref가 저장된다.
PASS일 때 reason_code가 null인 것은 오류가 아니라 정상이다. HOLD/HUMAN_REVIEW일 때 중단 사유를
reason_code에 넣는다.

UI의 3갈래 분류:

  "무슨 통계"
    PREPROCESS부터 SEMANTIC_MATCH까지: 어떤 통계를 선택했는지

  "어떤 데이터"
    EVIDENCE_CELL, OFFICIAL_VALUE_FETCH: 어떤 공식 셀과 값을 사용했는지

  "어떻게 검증"
    CALCULATION, VERDICT: 어떻게 계산하고 판정했는지

최근 CPI 배추 증감률 성공 예시의 추적:

  무슨 통계
    CLAIM_PARSE       PASS
    SEMANTIC_MAPPING  PASS
    CATALOG_SEARCH    PASS
    HARD_GUARD        PASS  output_ref=registered_growth_profile
    SEMANTIC_MATCH    PASS  output_ref=exact_registered_profile

  어떤 데이터
    EVIDENCE_CELL         PASS
    OFFICIAL_VALUE_FETCH  PASS

  어떻게 검증
    CALCULATION  PASS
    VERDICT      PASS

초기에는 최종 Verdict만 추적되거나 앞쪽 branch만 표시되던 문제가 있었으나, 공통 recorder를
추가하고 batch/UI/등록형 CPI 경로에 단계 이벤트를 연결해 전체 추적이 채워지도록 수정했다.

관련 파일:

  schemas/pipeline_trace.py
  core/pipeline_trace.py
  core/verification_trace.py
  core/claim_verification_service.py
  core/trace_presentation.py
  tests/unit/test_pipeline_trace.py
  tests/unit/test_verification_trace.py
  tests/unit/test_trace_presentation.py

21. 현재 전체 파이프라인의 구현 상태
------------------------------------

다음 핵심 Pipeline의 모듈과 테스트는 모두 존재한다.

  Article
    -> 전처리
    -> Claim Extraction
    -> Claim Split
    -> 12 Slot Parsing
    -> Semantic Standard Mapping
    -> KOSIS Semantic Catalog Search
    -> Hard Guard
    -> Semantic Matching
    -> Match Candidate
    -> Evidence Cell Resolution
    -> KOSIS Official Value Fetch
    -> Deterministic Calculation
    -> Verdict
    -> Evidence 표시 / Review handoff / Pipeline Trace

다만 "파이프라인 모듈이 전부 구현됐다"는 말과 "임의의 모든 뉴스 통계 Claim을 AUTO 판정한다"는

기사시점 근거가 등록 또는 실시간 해석되어야 AUTO로 갈 수 있다.

25. 결론
--------

CLAFACT-AUTO는 현재 "기사의 수치 문장을 구조화하고, KOSIS 후보를 안전하게 걸러서, 정확한 공식
Evidence를 조회하고, Python으로 계산해 판정하며, 전 과정을 추적하는" Core Engine과 MVP UI를
갖춘 상태다.

현재 가장 중요한 성과는 단순 MATCH 표시가 아니라 다음 세 가지가 함께 작동한다는 점이다.

  - 공식 근거가 확정된 Claim은 AUTO 판정과 KOSIS 원문 근거를 제공한다.
  - 불확실한 Claim은 억지로 결론 내리지 않고 구체적인 reason code와 함께 HOLD한다.
  - 성공과 중단 모두 3갈래 Pipeline Trace와 버전 정보로 재현 가능하다.

다음 개발의 핵심은 파이프라인을 새로 만드는 것이 아니라, 더 많은 KOSIS 통계표에 대해 공식
metadata와 Evidence 좌표를 자동으로 해석해 안전한 AUTO 범위를 넓히는 것이다.


26. HCX 12슬롯 Structured Output와 emit_claim 보강
-------------------------------------------------

기존 HCX responseFormat에는 ClaimSchema의 12개 의미 슬롯 중 dimension, comparison, condition이
명시되지 않았고, nullable 필드가 생략 가능한 형태였다. 이를 다음과 같이 보강했다.

  - canonical Claim JSON Schema를 독립 모듈로 분리
  - 12개 의미 슬롯과 메타 필드 총 16개를 모두 required 키로 지정
  - 값이 없는 필드는 키를 생략하지 않고 명시적 null 사용
  - 문자열: [string, null], 값: [number, null], 매핑: [object, null]
  - dimension, comparison, condition은 문자열 값만 갖는 nullable map
  - 추가 필드는 additionalProperties=false로 거부
  - HCX 반환값도 strict ClaimOutputPayload로 재검증하여 누락 키를 기본값으로 숨기지 않음

선택형 Function Calling 경로에는 emit_claim 한 개만 추가했다. HCX 공식 사양상 Structured Outputs와
Function Calling은 같은 요청에서 함께 사용할 수 없으므로, 기본 Structured Output extractor와
선택형 Function Calling extractor는 상호 배타적으로 동작하고 동일한 canonical schema를 공유한다.

emit_claim은 모델이 실제 Python 함수를 선택·실행하는 dispatcher가 아니다. toolCalls의 함수형·이름·
개수·arguments를 검증하고 ClaimSchema로 변환하는 typed return envelope이다. 잘못된 함수명, 복수
호출, 문자열 arguments, 누락·추가 필드, 잘못된 타입은 모두 거부한다.

HCX에 노출되는 함수는 emit_claim 하나뿐이다. 다음 단계는 계속 Python이 직접 통제한다.

  Semantic Mapping -> Catalog Search -> Hard Guard -> Semantic Matching
  -> Evidence Cell -> KOSIS API/Snapshot -> Calculation -> Verdict
