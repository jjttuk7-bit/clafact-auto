기준일: 2026-08-26

1. 이 작업의 목적
======================================================================

이 작업의 목적은 특정 Claim 몇 건을 억지로 통과시키는 것이 아니다.

목적은 다음과 같다.

1) 공식 근거까지 판정된 Claim에서 성공 조건을 찾는다.
2) 성공 조건을 특정 문장이나 Claim 번호가 아닌 재사용 가능한 규칙으로 만든다.
3) 같은 조건을 가진 미해결 Claim에 규칙을 적용한다.
4) 실제 KOSIS API와 공식 작성기관 자료를 다시 조회한다.
5) 개선 전후 결과와 공식 근거를 기록한다.
6) 이후 들어오는 새로운 기사에도 같은 규칙을 적용한다.

따라서 핵심 성과는 “15건 통과”라는 숫자만이 아니다.
무엇을 어떻게 연결했기 때문에 공식 판정이 가능해졌는지를 규칙과 근거로 남긴 것이 핵심이다.

2. 전체 1,542건에서 직접값 작업 범위가 만들어진 과정
======================================================================

전체 원장에는 1,542개의 Claim이 있다.
이를 검증 방법에 따라 직접값, 증감량, 증감률, 비중, 최고·최저, 순위,
복수 Claim 분리, 문맥 보완 유형으로 다시 나눴다.

이 가운데 이번 작업 범위는 8번 직접값으로 분류된 부모 Claim 381건이다.

직접값이란 기사에 적힌 값을 같은 기간의 공식값과 직접 비교하는 검증 방식이다.
예: “2025년 6월 취업자는 2,909만1천 명이다.”

그러나 ‘직접값’이라는 분류만으로 KOSIS API 값을 바로 조회할 수 있는 것은 아니다.
KOSIS에서 실제 값을 조회하려면 해당 Claim에 맞는 공식 통계표, 항목, 기간,
대상 집단, 분류 코드, 단위와 기사 작성 당시 공표 여부까지 확정해야 하기 때문이다.

381건을 다시 점검한 결과는 다음과 같다.

- 입력 전 차단: 21건
  연령, 기간, 상품번호처럼 통계값이 아닌 숫자를 기사값으로 잘못 잡은 경우이다.

- 단일 수치 부모 Claim: 133건
  한 문장에서 검증 대상 수치가 하나인 경우이다.

- 복수 수치 부모 Claim: 227건
  한 문장에 기사값, 비교값, 증감값, 환산값 등이 함께 있는 경우이다.

- 복수 수치 227건을 분리한 결과: 자식 Claim 290건
  숫자마다 역할과 검증 대상을 따로 기록했다.

- 다른 검증 유형으로 이동: 100건
  증감량 47건, 증감률 27건, 최고·최저 24건, 순위 1건, 비중 1건이다.

- 재분류 후 8번 직접값으로 남은 상세 Claim: 230건

주의할 점은 381건은 부모 Claim 수이고, 230건은 복수 문장 분리와 재분류 후의
상세 Claim 수라는 것이다. 두 숫자는 같은 단계의 분모가 아니다.

======================================================================

재분류된 직접값 상세 Claim 230건을 공식 조회 경로로 실행한 결과,
처음에는 10건이 공식 근거까지 완료됐다.

- KOSIS 공식 API 근거: 9건
- 공식 작성기관 문서 근거: 1건
- 기사값과 공식값 일치: 10건
- 불일치: 0건

10건은 다음 5개 공식자료 경로로 묶였다.

1) 관세청 무역수지 누계 공식문서: 1건
   - 연간 누계 무역수지 적자·흑자 Claim
   - KOSIS 표보다 관세청 공식 발표문이 해당 시점 누계값을 직접 제공했다.

2) 월간 전국 전체 취업자 수: 5건
   - KOSIS 표: DT_1DA7001S
   - 항목: T30
   - “취업자”, “취업자 수”, “15세 이상 취업자” 표현이 같은 공식 총계 항목으로 연결됐다.

3) 월간 전국 전체 실업률: 1건
   - KOSIS 표: DT_1DA7001S
   - 항목: T80
   - 세부 연령·학력 조건이 없는 전국 월간 실업률 Claim이었다.

4) 월간 연령별 고용률: 2건
   - KOSIS 표: DT_1DA7002S
   - 항목: T90
   - 15~29세, 65세 이상처럼 Claim의 연령 범위를 공식 연령 코드로 연결했다.

5) 분기 연령·학력별 실업률: 1건
   - KOSIS 표: DT_1DA7105S
   - 항목: T80
   - 연령과 학력 두 조건을 모두 공식 분류 코드에 연결했다.

4. 처음 10건이 통과한 이유
======================================================================

10건은 우연히 API 응답이 왔기 때문에 통과한 것이 아니다.
다음 조건이 모두 맞았기 때문에 공식 판정이 가능했다.

1) 검증 대상 수치가 원문에 실제로 존재했다.
2) 기사값과 비교값·증감값·연령·기간 숫자가 구분됐다.
3) 지표가 취업자 수, 실업률, 고용률, 무역수지처럼 구체적이었다.
4) 기준시점과 주기가 공식 통계표의 월·분기·누계 주기와 맞았다.
5) 전국 전체, 연령, 학력 같은 대상 조건이 공식 표의 분류 구조와 맞았다.
6) 명·천명, 달러·십억 달러처럼 기사 단위와 공식 단위를 환산할 수 있었다.
7) KOSIS 또는 공식 작성기관에서 실제 값과 공표 근거를 조회했다.
8) 공식값 조회 결과를 Python 계산으로 기사값과 비교했다.

즉 성공의 핵심은 “직접값”이라는 이름이 아니라,
Claim 조건과 공식자료 좌표를 정확하게 연결한 것이다.

5. 성공 10건에서 만든 5개 재사용 규칙
======================================================================

성공 사례를 그대로 복사하지 않고 다음과 같은 적용 조건으로 규칙화했다.

규칙 1. 관세청 무역수지 누계 공식문서 경로
- 적용 조건: 무역수지 + 누계기간 + 적자·흑자 부호가 명확한 Claim
- 공식 경로: 관세청 공식 보도자료
- 안전 조건: 기간, 대상국, 적자·흑자 부호가 원문과 공식문서에서 모두 일치해야 한다.

규칙 2. 월간 전국 전체 취업자 수 경로
- 적용 조건: 취업자 수 + 월간 + 전국 + 전체 또는 15세 이상
- 공식 경로: DT_1DA7001S / T30
- 안전 조건: 산업·지역·연령 세부집단 Claim에는 이 총계 규칙을 적용하지 않는다.

규칙 3. 월간 전국 전체 실업률 경로
- 적용 조건: 실업률 + 월간 + 전국 + 세부 차원 없음
- 공식 경로: DT_1DA7001S / T80
- 안전 조건: 연령·학력 조건이 있으면 전체 실업률 좌표를 사용하지 않는다.

규칙 4. 월간 연령별 고용률 경로
- 적용 조건: 고용률 + 월간 + 전국 + 연령 범위 존재
- 공식 경로: DT_1DA7002S / T90
- 안전 조건: Claim의 연령 표현과 공식 연령 코드가 정확히 대응해야 한다.

규칙 5. 분기 연령·학력별 실업률 경로
- 적용 조건: 실업률 + 분기 + 전국 + 연령과 학력이 모두 존재
- 공식 경로: DT_1DA7105S / T80
- 안전 조건: 연령 또는 학력 중 하나라도 없으면 이 표를 강제로 선택하지 않는다.

이 규칙들은 특정 Claim 번호나 문장을 조건으로 사용하지 않는다.
지표, 주기, 지역 범위, 연령, 학력 등 Claim의 의미 조건으로 적용된다.

6. 파이프라인에 실제로 반영한 내용
======================================================================

1) 5개 공식자료 경로를 반복 도메인 규칙으로 등록했다.
2) 공식 표가 의미하는 대상 범위를 함께 기록했다.
3) 연령·학력 조건이 필요한 표는 두 조건을 모두 요구하도록 만들었다.
4) “15세 이상”, “전체”, “청년층” 같은 표현을 공식 구조정보와 연결했다.
5) 복수 수치 문장에서 검증 대상 수치만 정확하게 연결하도록 보강했다.
6) 저장된 구조화 결과가 오래된 오류를 가진 경우에도 원문에서 정확히 하나의
   대상 수치가 확인될 때만 안전하게 복구하도록 했다.
7) 기사 문맥에서 연령을 보완하는 기능은 연령×학력 실업률에만 제한했다.
8) KOSIS 공식값과 공표정보를 실제 조회한 뒤에만 최종 판정하도록 유지했다.
9) 규칙 파일이 바뀌면 이전 실행 결과를 잘못 재사용하지 않도록 실행 서명에 포함했다.
10) Streamlit 대시보드, 배치, CLI가 같은 공통 파이프라인을 사용하도록 반영했다.

7. 같은 패턴의 미해결 Claim 재실행 결과
======================================================================

정확한 재실행 대상은 5건이 아니라 7건이다.
5건은 재실행 후 공식 판정이 완료된 건수이다.

- 재실행 대상: 7건
- 공식 판정 완료: 5건
- 기사값과 공식값 일치: 5건
- 불일치: 0건
- 보류: 2건

세부 결과는 다음과 같다.

1) 월간 전국 전체 취업자: 3건 실행
   - 2건은 공식 좌표를 확정해 기사값과 공식값이 일치했다.
   - 1건은 공식 좌표까지 찾았지만 기사 작성 당시 공표 여부를 확정하지 못해 보류했다.

2) 월간 연령별 고용률: 2건 실행
   - 1건은 15~29세 공식 연령 좌표와 연결돼 일치했다.
   - 1건은 공식 좌표까지 찾았지만 기사 작성 당시 공표 여부를 확정하지 못해 보류했다.

3) 분기 연령·학력별 실업률: 2건 실행
   - 30대·고졸 Claim은 연령과 학력 좌표를 모두 연결해 4.2% 일치 판정을 받았다.
   - 25~29세·고졸 Claim은 기사 문맥에서 누락된 연령을 안전하게 복구한 뒤
     연령과 학력 좌표를 모두 연결해 5.5% 일치 판정을 받았다.

보류 2건을 강제로 통과시키지 않은 이유는 규칙 실패가 아니라 공표시점 때문이다.
현재 KOSIS 값이 존재하더라도 기사 작성일 당시에 발표된 값인지 확인되지 않으면
그 기사의 근거로 사용할 수 없기 때문에 보류가 올바른 결과다.

8. 10건에서 15건으로 증가했다는 의미
======================================================================

- 기존 원장의 공식 근거 완료: 10건
- 이번 규칙 적용 후 추가로 원장에 확정한 완료: 5건
- 누적 공식 근거 완료: 15건

이 수치는 직접값 230건 전체가 해결됐다는 의미가 아니다.
또한 5개의 문장을 개별 예외 처리했다는 의미도 아니다.

의미는 다음과 같다.

1) 처음 성공한 10건에서 반복 가능한 공식자료 경로 5개를 발견했다.
2) 경로별 적용 조건과 적용 금지 조건을 코드와 데이터로 등록했다.
3) 같은 조건의 다른 Claim 7건에 다시 적용했다.
4) 5건이 실제 공식 API 값·좌표·공표정보까지 갖춘 판정으로 연결됐다.
5) 2건은 공표시점이 불충분해 정확한 단계에서 보류됐다.

따라서 이번 결과는 “통과 숫자 5건 증가”와 함께
“새로운 유사 Claim에 재사용할 수 있는 5개 공식자료 연결 규칙을 확보”한 결과이다.

9. 새로운 Claim에 규칙이 적용되는 방식
======================================================================

예를 들어 새로운 기사에 다음 문장이 들어오면,

“2025년 7월 15세 이상 취업자는 2,900만 명이다.”

파이프라인은 다음 순서로 처리한다.

1) 기사값 2,900만 명과 기준시점 2025년 7월을 구조화한다.
2) 지표를 취업자 수로 확정한다.
3) 월간·전국·15세 이상 전체 조건을 확인한다.
4) 월간 전국 전체 취업자 규칙의 적용 조건과 대조한다.
5) KOSIS 공식 검색과 구조정보 API를 실제로 조회한다.
6) DT_1DA7001S / T30의 공식 좌표가 Claim 조건과 일치하는지 확인한다.
7) 2025년 7월 공식값과 공표정보를 실제 조회한다.
8) 기사값과 공식값을 Python으로 비교한다.
9) 일치·불일치 또는 정확한 보류 사유를 기록한다.

규칙은 공식 조회를 생략하는 정답표가 아니다.
공식 조회에 필요한 후보 경로와 안전 조건을 제공하고,
실제 API 결과가 조건을 만족할 때만 판정하게 만드는 장치이다.

10. 이번 방식에서 계속 지켜야 할 평가 기준
======================================================================

앞으로 다른 직접값 묶음도 다음 기준으로 평가해야 한다.

1) 성공 건수만 기록하지 않고 개선 전후 상태를 함께 기록한다.
2) 성공한 Claim마다 공식 좌표, 공식값, URL, 응답 해시, 공표 근거를 남긴다.
3) 어떤 공통 조건 때문에 성공했는지 설명한다.
4) 특정 Claim 번호나 문장에만 작동하는 예외 처리는 성공으로 인정하지 않는다.
5) 같은 규칙의 다른 Claim을 다시 실행해 재현성을 확인한다.
6) 잘못된 공식표를 선택한 불일치가 없는지 확인한다.
7) 공식 근거가 부족하면 정확한 단계와 이유로 보류한다.
8) 신규 기사도 대시보드의 같은 공통 파이프라인에서 같은 결과가 나와야 한다.

11. 현재 결론과 다음 작업 원칙
======================================================================

이번 작업으로 직접값 유형 전체가 끝난 것은 아니다.
그러나 처음 10건을 단순 성공 사례로 남기지 않고 5개 공식자료 경로 규칙으로 만들었고,
같은 패턴 7건을 재실행해 5건을 추가 완료하고 2건을 정확히 보류했다.

다음 작업도 같은 방식으로 진행해야 한다.

남은 직접값 Claim에서 같은 실패 원인 묶음 선택
→ 묶음 전체의 공통 의미 조건 확인
→ 실제 성공 사례에서 일반 규칙 설계
→ 특정 Claim 예외가 아닌 공통 엔진에 구현
→ 같은 묶음만 실제 공식 API로 재실행
→ 개선 전후 성공·실패·보류와 모든 공식 근거 기록
→ 재현 조건을 만족할 때만 다음 묶음으로 이동

이 방식이 Claim을 하나씩 수작업으로 통과시키는 것과 다른 점이다.
